# ADR 0021: The package keeps the order of the file, and the concept description gaps close in the view

**Status:** Accepted

## Context

Work package 16 closes the gaps of the concept description editing that the [acceptance audit](../v1-acceptance-audit.md) found: the view orders (F-EDT-05 AC10), deleting a value list (AC7), SAMM (AC18), the embedded display (F-EDT-03 AC15, F-EDT-05 AC14), presets that replace a blank member (F-EDT-05 AC16, F-EDT-06 AC14, F-EDT-07 AC1), and four criteria of the references (F-EDT-11 AC1, AC5, AC15, AC16). Probes of the pinned SDK and a reading of the verification code of Package Explorer, which is local, showed:

- The package holds its shells, submodels and descriptions in `SetIdentifiableStore`, which is backed by a Python `set`. Its order depends on the memory addresses of the objects, and changes from run to run. A file that was read and written again lost the order of its descriptions. The plan (D16) took this as a reason to give the view orders of descriptions no effect on the file.
- The store only adds, discards, removes, tests, counts and iterates its backend. A `dict` as the backend keeps the order of `add`, and everything else of the store stays as it is, including finding an object whose id changed.
- A qualifier needs a type of at least one character, an extension a name, and a reference at least one key. The SDK refuses a blank one when it is made, when the type is cleared, and when a file holds one, also in failsafe mode. A data specification record needs content. No blank qualifier or record can exist in a package.
- V3.1 has no key type for a stored file. `FILE` is the key type of the File element.
- The tree of the package shows each kind of object under a node of its own, and the legacy item models make a row for each object. Putting descriptions under the elements that use them would change every model that follows a change, and the commands that report positions.
- The constraints AASc-3a-004 to 007 are in the published text of Part 3a (IDTA-01003-a V3.1.1, `aas-specs-iec61360`), with the sets of data types. None of the 132 bundled templates sets one of the categories that they are about, so none breaks them.

## Decision

- **The store keeps the order of the file.** `domain/ordered_store.OrderedIdentifiableStore` is a `SetIdentifiableStore` with an ordered backend. `Package` and the reader of `package_io` use it, so a read follows the order of the file and a write follows the order of the store. A delete that is undone puts the object back at its place. A view never gets a position of the store as a row, because the rows of a node are one kind of object, so `edits._row_of` leaves it out of the change.
- **The six view orders of Package Explorer, and the name.** `ConceptOrder` has the four of version 1 (name, idShort, id, first use) and three new ones: *List index*, which is the order of the store, *By submodel elements*, which counts only the semantic ids of elements, and *Structured*. A view order is still state of the view and never changes the package. The three new ones **order the one list**, and do not make the branches or the nesting of the original. *Structured* lists what an Aspect reaches first (following the links of the SAMM elements, depth first, each once), then what submodels use, then the rest by name. The ranks are worked out when the order is chosen, like the first use order, and do not follow later edits.
- **A permanent sort.** `concepts.sort` writes the order of the view into the store as one undo step (`application/operations/sort_concepts`). It sorts by name, idShort, id and first use. *List index*, *By submodel elements* and *Structured* give `The file cannot keep this order, so nothing was sorted`, and nothing changes, as the original does (AC12). A sort that changes nothing says so. After a sort the view goes back to the list index (AC11). The shells and submodels keep their places in the store, and the descriptions take the places of the descriptions.
- **The embedded display is read-only and collapsed.** `ui/embedded_concept.EmbeddedConceptPanel` is a widget of its own, under the attributes of the tab of a submodel or an element with a semantic id. It shows the description that the semantic id names (the rule of ADR 0014), as one line, and the attributes of the first IEC 61360 record when expanded. A button opens the description in the tab, where it is edited, and Back returns. A semantic id that names nothing shows `The package has no concept description that this semantic id names`. The original hides the display when the order is *By SubmodelElements*, because the descriptions are nested in its tree. They are not nested here, so hiding it would show them nowhere, and the display stays (different on purpose). The original's embedded display is editable. This one is not, because the description has its own tab and its own actions, and one place to edit means one place to get right.
- **SAMM is recognized, not modeled.** `domain/samm` finds a SAMM element in an extension (the semantic id is one key with the URN of a known type in version 1.0.0 with `bamm`, or 2.0.0 and 2.1.0 with `samm`), and reads the links of its JSON. AC18 asks for two things, and both are done: the tab of such a description lists `id` and `administration` before the referable attributes, and the hint *a concept description has a data specification* (`EDT-HINT-NO-DATA-SPEC`, new, a warning) is not given for it. Editing the elements, the namespaces, and the import and export of Turtle belong to F-SMT-05 and F-EXC-08, which are experimental features outside F-EDT.
- **A value list is deleted in the record dialog.** The dialog lists the pairs, and removes one or all. A record without pairs has no value list (a list has at least one pair).
- **No preset replaces a blank member, because there is none.** The criteria describe the result of a two-step flow of the original: a default empty qualifier or record, and then the preset. The editor adds the member of the preset to an owner that has none, and the result is the same: one qualifier or record with the values of the preset. Tests assert that end state, and probes of the SDK assert that no blank one can exist.
- **The file filter is in the chooser of the File element.** A reference cannot point at a stored file in V3.1, so the reference picker has no file leaf. `FileChoiceDialog` lists the stored files and nothing else, and the File element takes the part name as its value.
- **Create empty adds a description and leaves the semantic id.** It is available on the node of the descriptions and on submodels and elements, adds a description with a `urn:uuid:` id and nothing else, and selects it. The original's tooltip promises an assignment, but its code does none, and the criterion says that the semantic id is unchanged. *Assign concept description* puts it in.
- **Create from semantic id explains itself.** It is on for any single submodel or element, and says `... has no valid semantic id, so there is no concept description to create.` when there is none (AC16). Before, it was off and said nothing.
- **The picker lists the other open packages.** `PickerSource` and `candidates_in` list the targets of several packages, and the picker names the package of each and can leave the others out. A target in another package gives the same reference as one in this package, an external reference to its id or a model reference through its path, and the field reports it as outside of this package.
- **AASc-3a-004 to 007 are rules.** `domain/validation/rules/concepts.py` reports an error for a concept description whose category is PROPERTY, VALUE, REFERENCE, DOCUMENT or QUALIFIER_TYPE and whose IEC 61360 record has a data type that does not fit, or none where one is mandatory. Errors ask once before a save (D5).

## Consequences

- The order of a file survives an open and a save for the shells, submodels and descriptions. D16 held for the descriptions only because the editor chose a set store. Moving shells, submodels and descriptions (the plan lists it as out of scope) is possible now, and is not done.
- A stored order is the order in which objects were added. A file that was written by another tool is read in its order, and a description that is added in the editor comes last until a sort.
- A package that was saved by an older version of the editor has the arbitrary order that the set gave. It is read as it is.
- The orders that use ranks (first use, by elements, structured, and now list index) are worked out when chosen and stay as they were when the package changes. Choose the order again to refresh it.
- The embedded display works out the description again after each change of the package, which walks the object ids once. It does not use the reference index, which would walk everything.
- A save of a package that sets a category of a description and no fitting data type asks first. The bundled templates are not affected.
- `EDT-HINT-NO-DATA-SPEC` is a hint (hints mode only) for every description without a record. Of the 6778 descriptions of the 132 bundled templates, 45 in 3 templates have none.

## Alternatives considered

- **Keep the set store, and rank the view by the order of the file as it was read.** Rejected: the order of a save would still be arbitrary, so the list index would show something that a save does not write, and a permanent sort could not exist.
- **Nest the descriptions under the elements in the tree for *By submodel elements*.** Rejected for this package: it changes the item models, the delete and paste flows, and every command that reports a row, while the tabs of the layout are being changed by another work package. The display in the tab shows the description where the user is.
- **Edit the description inside the embedded display.** Rejected: two places to edit one object, and a long form in every tab of an element.
- **Hide the embedded display for *By submodel elements*.** Rejected: it would leave the description visible nowhere.
- **Build a SAMM editor.** Rejected for this package: F-SMT-05 is experimental, has 14 defects of its own listed in its design document, and needs a decision on the SAMM version to support.
- **Replace an existing qualifier of the same type when a preset is added.** Rejected: the criteria say a *blank* one is replaced. Replacing a filled one loses data, and the add already skips the owner and says why (AASd-021).
- **Report AASc-3a-004 to 007 as warnings.** Rejected: the specification says shall, and the original reports errors. No bundled template is affected, and an error asks once before a save.
